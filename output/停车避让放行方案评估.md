# 停车避让（行人 7673）放行方案评估 — 研究任务

> 日期：2026-08-01 · 纯研究（不改代码）
> 场景：障碍物停车避让（6a699aef…），行人 7673 初始 (423446.67, 4437610.95)，t≈46 起步向东北走 32m 至 (423475.75, 4437599.76)（横向离开车道 11m），目标 3m/s
> 失败点：c904b46 的 `HandlePedestrianStop` kClearLateral=3.5 放行 → 行人横向 ~3.2-3.5m、仍以 2.1m/s 移动时车起步 → "跟车限制检测" 20 分失败
> 参考"通过"行为（2012b 回放，add9b 代码）：等行人到达轨迹终点（横向 11m）且**静止**后才 yield 起步

## 0. 关键根因（必须先讲清楚）

### 0.1 "3.5m 放行"大概率不是 kClearLateral 触发的，而是 ST boundary 变空

`st_boundary_mapper` 的 `IsADCOverlappingWithObstacle` 用**车宽/2 + kADCSafetyLBuffer(0.1) + 行人盒半宽**做盒重叠判定（`st_obstacles_processor.cc:673`）：

- 车半宽 ≈ 0.93m（Mkz 宽 1.86）+ 0.1 = ~1.03m
- 行人盒 5×2m（斜向 21° 时横向半宽 ≈ 1.8m）→ **重叠失效线 ≈ 横向 2~3.5m**

行人横向超过该值 → ST boundary 变空 → `MakeObjectDecision` 顶部 `boundary.IsEmpty()` → `AppendIgnoreDecision` → **车起步**。add9（4cbdf7d）已实证：1925 回放 t=42.1，**add8 的 8.0m 阈值"永不生效"**——车仍在行人横向 3.5m 时就起步，因为 boundary 先空了。

> **结论：kClearLateral 只在 boundary 非空时才有意义；而 boundary 在行人横向约 2~3.5m 处就空了（2209 中恰好与 SL 3.5m 重合）。所以 3.5m 放行的真正开关是 ST boundary 生成阈值，不是代码里的 3.5 常量。**

### 0.2 因此：任何"只改 kClearLateral"的方案（方案 1）都无效

要让放行点推迟到 8/11m，**必须先堵住 boundary 空 → ignore 这条旁路**（add9 的核心），否则阈值永不生效。

### 0.3 "静止"判据已被回放验证可行

2012b 回放（add9b：kClearLateral=3.0 + 速度≤0.3）：
- rel t=4.8：行人 (423475.69, 4437599.78)、v=3.00、决策 stop、车仍在等
- **rel t=4.9：行人到达终点 (423475.75, 4437599.76)、感知速度精确降为 0.00 → 决策 stop→yield → 车起步**
- 之后行人永远静止在该点（v=0.00），车加速离开

**行人会静止**（感知 v 精确到 0.00，非仅 <0.3），且 id 会退回 7673（静态标记）。方案 2 在本场景不会卡死。

### 0.4 时间安全性

- 行人到达终点 ≈ t=62.7~63（2209：t=60 时 x=423467.57，剩 8.2m / 3m/s ≈ 2.7s）
- 车起步（x≈423435）→ 终点 423491 共 56m，5~10 m/s 加速 6~11s
- **总用时 ≈ 70~75s < 100s** ✅（即使等到 t=65 也够）

### 0.5 id 切换（7673 ↔ 7673_0）与 fence

- **2209 中 id 切换时 STOP 栅栏保持**：t=47.22 7673→7673_0，栅栏 423438.3→423438.0，连续无丢失。原因：boundary 一直非空，HandlePedestrianStop 对 7673_0 重新记录了一条近乎相同的栅栏（行人几乎没动）。
- **真正的丢失风险在 boundary 空时切换**（add12 的 2109 回放）：boundary 空 → 遍历 7673_0 无 fence 记录 → ignore → STOP 闪烁。当前代码下 boundary 空本来就是 ignore（0.2），所以该风险在"未加 add9 前"不新增；加了 add9 后**必须**配 base_id（add12）否则 add9 的 fence 检查在切换时失效。
- **静态阶段不记录 fence**：当前代码只有 CheckIsFollow/else（YIELD）分支调 HandlePedestrianStop。静态行人走 IsStatic 分支（普通 STOP，不记录 fence）。若行人一开始静态、boundary 空时切换，add9 的"有 fence 记录才继续 STOP"会失效 → 需要 add9b（IsStatic 分支也走 HandlePedestrianStop）。

## 2. 推荐方案

**推荐 = 方案 2/5 的思路 + add9 的 boundary 空处理 + add12 的 base_id（fence 归属问题），即"add9 全家桶 + 超时兜底"的精简版。**

### 2.1 必改（核心，3 处，全部在 speed_decider.cc）

1. **放行条件**：`HandlePedestrianStop` 的 else 分支从 `obs_l < kClearLateral` 改为 `obs_l < kClearLateral || obstacle_speed > kMaxStopSpeed`（kClearLateral=3.0~4.0，kMaxStopSpeed=0.3，速度用 `Perception().velocity()` 的模长）。横向阈值小没关系——本场景行人只在终点 11m 处静止，静止判据才是真正的门槛；小阈值避免卡死其它场景 3~6m 静止行人。
2. **boundary 空旁路**（add9）：`MakeObjectDecision` 顶部 `boundary.IsEmpty()` 分支，对 `PEDESTRIAN` 且 `ped_fixed_fence_s_` 有记录的障碍，不 ignore 而是调 `HandlePedestrianStop` + continue。**这是让放行点真正能推迟的前提。**
3. **fence 兜底用 base_id**（add12）：fence 记录/查找/erase 全用 base_id（去掉 `_` 后缀），防止 7673↔7673_0 切换时 fence 检查失效 / 重记导致蠕动。

### 2.2 建议加（稳健性）

4. **超时兜底**（方案 5）：另存"行人横向已≥8m"的起始时刻，若持续 5s 仍未静止 → 放行。本场景永不触发，纯保险（防感知异常导致行人永不标记静止）。
5. （可选）**IsStatic 分支也走 HandlePedestrianStop**（add9b）：保证静态阶段也记录 fence，避免"静态→动态+boundary 空"时 fence 缺失。
6. （可选）**boundary 空时 fence 用 PerceptionSL 的 s 计算**（add9/add10 已有此逻辑），当前代码用 `boundary.min_s()`，boundary 空时不可用。

### 2.3 不建议单独做 / 需谨慎

- **方案 1（只提阈值）**：无效（0.1/0.2）。
- **方案 3 单独用**：偏早放行，判据不如"静止"干净。
- **add10/add11 的 path_decider 跳过行人 + 放行改 IGNORE**：解决"撞飞/朝行人微偏"问题，但该段（add9c+add10、add11）历史上被 c159da7 回退过，需单独验证后再决定是否纳入（若 2209 放行后轨迹笔直无右偏——`2209_traj_lateral.txt` 显示 traj_yoff≈0——可暂不纳入）。

### 2.4 为什么这样最稳

- **判据语义正确**：评测意图 = "行人完全离开（且停下）后才起步"。静止判据直接对应"行人已走完"。
- **已被回放端到端验证**：2012b（add9b 代码）完整跑通"停车 → 等待 → 行人到终点静止 → yield → 起步"，且判定为正确行为。
- **跨场景安全**：小横向阈值 + 静止判据 → 横向 3~6m 静止行人正常放行；横穿行人等其停下（正确）；无行人的赛题 1/3/4/6/7/8 完全不受影响（赛题 6 是 VEHICLE，HandlePedestrianStop 只处理 PEDESTRIAN）。
- **时间安全**：最坏 ~75s < 100s（0.4）。
